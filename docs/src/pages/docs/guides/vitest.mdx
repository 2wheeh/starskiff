# Vitest Setup [Start a configured topology once per test project]

`createGlobalSetup()` from `starskiff/vitest` starts the chains and relayers in a [declarative config](/docs/guides/config), passes their endpoints to test workers, and stops them when the project finishes. Install Vitest in your project; the adapter uses its standard [globalSetup](https://vitest.dev/config/globalsetup) and [provide/inject](https://vitest.dev/config/provide) interfaces.

## Declare the topology

```ts
// starskiff.config.ts
import { defineConfig, Instance, testAccounts } from 'starskiff';

export default defineConfig({
  chains: {
    wasm: {
      factory: Instance.wasmd,
      parameters: {
        chainId: 'wasm-test-1',
        accounts: [{ mnemonic: testAccounts[0].mnemonic, coins: '1000000000stake' }],
      },
      options: { timeout: 120_000 },
    },
  },
});
```

## Register global setup

Import the config directly from a setup file and export the generated setup function. This also keeps TypeScript config loading in Vitest's normal module pipeline.

```ts
// test/global-setup.ts
import { createGlobalSetup, type StarskiffContext } from 'starskiff/vitest';
import config from '../starskiff.config.js';

export default createGlobalSetup(config);

declare module 'vitest' {
  export interface ProvidedContext {
    starskiff: StarskiffContext<typeof config>;
  }
}
```

```ts
// vitest.config.ts
import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    globalSetup: './test/global-setup.ts',
  },
});
```

## Use endpoints in tests

```ts
// test/bank.test.ts
import { expect, inject, it } from 'vitest';
import { StargateClient } from '@cosmjs/stargate';

const { chains } = inject('starskiff');

it('connects to the configured chain', async () => {
  const client = await StargateClient.connect(chains.wasm.rpcUrl);
  try {
    expect(await client.getChainId()).toBe(chains.wasm.chainId);
  } finally {
    client.disconnect();
  }
});
```

`StarskiffContext<typeof config>` preserves the configured chain names. Each chain exposes `chainId`, `prefix`, `denom`, `rpcUrl`, `grpcUrl`, and `apiUrl`; EVM chains also have `evmUrl`. The context contains plain data, so Vitest can send it between processes. Instance methods, factories, and genesis account parameters stay in global setup.

## Ports and lifecycle

- Missing Cosmos ports, including the EVM port, are assigned automatically. Factories that do not support EVM ignore that field. Explicit port values are preserved; omit them when running multiple projects concurrently.
- Automatic chain ports are held during topology construction so they cannot be allocated twice, then released immediately before startup. Another process can still claim a port during that handoff.
- Chains start concurrently. Hermes starts only after all chains are ready, with an automatically allocated telemetry port unless one was configured.
- A setup failure waits for outstanding chain starts and then stops every created instance, including the instance whose start failed. Teardown stops relayers before chains and attempts every stop even if one fails.
- Each Vitest project gets its own topology. Test files within that project share chain state. In watch mode, the topology stays running across reruns until Vitest exits; it is not reset to genesis between tests or reruns.

For IBC, set distinct `parameters.chainId` values on the chains connected by Hermes and fund the relayer mnemonic in each chain's fee denom. Repeated pairs are preserved. `inject('starskiff').relayers` describes the configured chain-name pairs; it does not expose the IBC connection or channel IDs created during setup.

Custom Cosmos factories must accept object parameters and honor the standard Cosmos port fields. Source selection, accounts, chain IDs, and lifecycle options otherwise follow the selected factory's contract. Configure slow starts through each declaration's `options.timeout`.

## Runtime availability

Image-backed instances need Docker; binary-backed instances need their executable. Hermes needs its host binary. Global setup failures fail the test run; the adapter does not silently skip unavailable runtimes. Gate the integration project explicitly when your environment cannot run it.
